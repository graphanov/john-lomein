# john-lomein maintainer appliance 10/10 standard

This is the productization bar for shipping john-lomein as a reusable maintainer bot for another repository.

## Definition of a live instance

A live instance is not “a profile exists.” It is all of this:

1. **Five-role runtime** — `john-lomein-maintainer`, `john-lomein-forge`, `john-lomein-guide`, `john-lomein-overwatch`, and `john-lomein-learning-steward` are installed inside an isolated `runtime.hermes_home`.
2. **Source/runtime boundary** — product templates are canonical; runtime files are generated by `make deploy` and drift-checked by `make doctor`.
3. **Profile isolation** — profile-local SOUL, skills, config, tool HOME, Mnemosyne, and GitHub auth are present for every role.
4. **Discord guide boundary** — public guide gateway is separate from the scheduler gateway and gets the Discord token only in the guide profile.
5. **Cheap triggers, durable workers** — no-agent crons do only fast queue/capacity checks, then detach workers under `state/workers/` and `logs/workers/`.
6. **Issue-to-PR forge lane** — ready issue -> design -> overwatch critique -> implementation -> draft PR -> `@codex review`; `REVISE` deferrals retry automatically with prior critique context instead of silently parking ready issues.
7. **PR maintainer lane** — open PRs are pushed until latest-head CI/review/Codex clean, or an exact blocker is named; current-head clean Codex issue comments count, and duplicate `@codex review` requests for the same head are guarded.
8. **Release bundle lane** — clean PRs are grouped into a bundle and signaled to the owner; cron and the same-identity executor never merge or publish; executor dry-run must use the freshest generated bundle unless exact approval names a bundle, not stale `.last-signaled` notification state. An optional isolated v1 path may authenticate one exact Discord approval and merge one PR by squash only.
9. **Anti-stall / anti-spam / anti-collision** — workers write pid/state/heartbeat; overwatch alerts on stale pid/heartbeat and does not force-kill long agent work; queue health reports retryable forge deferrals separately from hard-deferred/KILL issues; maintainer triggers are suppressed for clean owner-gated PRs and Codex-pending PRs but wake on abandoned dirty checkouts; forge triggers stay silent when PR capacity is full or the PR queue has maintainer blockers; maintainer and forge workers cannot run concurrently on the shared checkout.
10. **Publicization** — public template files are privacy-scanned; `instance.yaml`/`bot.yaml` stays private; setup/uninstall/doctor/dry-run paths exist.

## Authority ladder

| Action | Default authority |
|---|---|
| Read repo/GitHub/CI/reviews | allowed |
| Patch scoped feature/PR branch | allowed only when `runtime.mutation_enabled: true` |
| Commit/push draft PR branch | forge/maintainer allowed within gates |
| Trigger `@codex review` | allowed for current-head PR review |
| Mark draft PR ready | exact evidence packet; current runtime cannot perform it directly, but may submit once to the installed isolated broker |
| Inline review reply / resolve review thread | inline/current-thread action unavailable; one exact outdated-thread packet may be submitted to the installed isolated broker, while the current runtime cannot perform it directly |
| Merge PR | exact owner approval + separately isolated protected broker; current v1 is one PR and squash only |
| Publish npm / dispatch publish workflow | blocked until protected broker + immutable-artifact lane |
| Release/GitHub Release | blocked until a dedicated protected release-publication lane exists |
| Force-push, branch protection, settings, secrets | no-go in the current runtime |

## Required verification

Run for every instance after product changes:

```bash
make deploy INSTANCE=/path/to/instance
make smoke-all INSTANCE=/path/to/instance
make install-supervisor INSTANCE=/path/to/instance
make install-guide-gateway INSTANCE=/path/to/instance
make doctor INSTANCE=/path/to/instance
make queue-health INSTANCE=/path/to/instance
make worker-status INSTANCE=/path/to/instance
make release-health INSTANCE=/path/to/instance
make release-broker-status INSTANCE=/path/to/instance
make privacy-scan
```

`release-broker-status` is a disabled-state inspection for normal instances. It becomes a readiness gate only when both runtime mutation and `release.protected_broker_enabled` are true. In that mode, public config files alone are insufficient: the signer authorization and authenticated broker socket must both be effective.

A healthy report must distinguish:

- **alive** — profiles/crons/supervisors/auth/checkouts exist;
- **visible** — blockers and state changes route to the configured notification channel;
- **effective/gated** — PRs are clean/moving/blocker-named without duplicate Codex spam or stale-worker stalls, ready issues are covered, retry-due/capacity-blocked, or hard-deferred with an explicit reason, and clean PRs are in a human-gated bundle.

## Publish truth

john-lomein can prepare package/version/workflow evidence, but live npm publish is fail-closed with `publish_requires_protected_broker`. The future lane must combine trusted publishing, immutable dispatch, digest-verified tarballs, and a registry-authorized job that never executes repository tests or lifecycle scripts.

If the package version is already published, a merge bundle may still be ready, but the owner approval text must say **DO NOT publish** until a version-bump/release-sync PR makes the package version unpublished.

A successful protected-release receipt currently proves the exact squash merge and signed GitHub readback. It does not itself prove a later credential-free repository-test run; that result must remain a separate artifact until the automatic post-merge verifier handoff is implemented.
